## Data loss incident, 2026-10-05 (fixed)
He opened the app and his Scroll was empty. Cause: to swap the exe in without the NSIS installer I had been force-killing the app (`Stop-Process -Force`) mid-write. The whole state sits under ONE localStorage key (`osrs_todo_state_v1`, ~785KB), WebView2's leveldb recovery dropped the half-written key, the page started fresh and the first save buried it. Recovered by reading orphaned .ldb table files (see scratchpad/ldbread.py: a minimal SSTable reader using cramjam for snappy).
**NEVER force-kill the app.** Close it with `CloseMainWindow()` + `WaitForExit`, then copy the exe.
Fixes shipped (commit e18c4ce): a mirror of the non-wiki state under `osrs_todo_state_v1_mirror`; plain JSON backups written by the desktop app to `Documents\OSRS Buddy\backups` (launch, hourly when dirty, before imports, on close; last 20 kept, see app/src-tauri/src/vault.rs); and a load path that sets `saveLock` so a failed read can never be written over, with a restore prompt and setup suppressed.
## The real cause of the repeated data loss (2026-10-06)
Not storage corruption: **two app instances on one WebView2 profile**. `CloseMainWindow()` often does NOT exit OSRS Buddy, so relaunching after installing a build started a second copy; it can't open the leveldb the first holds, Chromium logs "Creating DB ... since it was missing" and starts an empty one, and that empty state saves over everything. Evidence lives in `%LOCALAPPDATA%\com.joshf.osrsbuddy\EBWebView\Default\Local Storage\leveldb\LOG`.
Fixed with `tauri-plugin-single-instance` (second launch focuses the existing window) and by restoring the newest `Documents\OSRS Buddy\backups` file automatically instead of prompting.
**Before installing a build:** close, then poll until both the `OSRS Buddy` process AND every `msedgewebview2.exe` whose command line contains `com.joshf.osrsbuddy` are gone. Never assume CloseMainWindow worked.

## THE ROOT CAUSE of a month of "data loss" (found 2026-10-17): the Claude desktop sandbox
This session runs inside the Claude desktop app's MSIX package. Anything launched or installed from here gets AppData virtualized into `C:\Users\joshf\AppData\Local\Packages\Claude_pzs8sxrjxfjjc\LocalCache\...`. The app I launched ran from the sandbox copy of the exe, an NSIS install run from here rewrote his Start-menu shortcut to that sandbox path, and his data ended up in two parallel copies (real vs LocalCache). ## Phone self-update, the working version (2026-10-18)
The document.write swap never actually applied: the old page's let/const globals stay in the window, so the new page's script throws on redeclaration (test only passed with a fake page).
